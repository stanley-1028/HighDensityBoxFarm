### 19.18 非功能需求（v2.1 新增：可读性 / 可维护性 / 可扩展性 / 安全性）

> 本节与 §19.1–§19.17 **同等强制**，是 v2 的发布门槛；不得以“功能先跑通”为由跳过。
> 目标顺序：**先让代码和文档可读、可改、可测，再堆功能**；结构简单优先于“聪明”的抽象；任何失败都不能破坏存档或让游戏崩溃。

#### 19.18.1 可读性（文档 + 标记 + UI）

**A. 文档集（保持简单，不膨胀）**

| 文件 | 内容 | 维护责任 |
|---|---|---|
| `docs/v2/README.md` | v2 一页索引：目标、模块地图、构建/测试命令、需求入口 | Lead |
| `docs/v2/ARCHITECTURE.md` | 分层/依赖方向/数据流/日 tick 顺序/关键决策摘要（含图） | Lead |
| `docs/v2/INTERFACES.md` | 核心接口与不变量；每个接口一屏内可读完 | Lead + 实现者 |
| `docs/v2/ADRS.md` | ADR-V2-001 室内农场；ADR-V2-002 平屋顶叠放；ADR-V2-003 存档 v2；ADR-V2-004 水模型 | Lead |
| `docs/v2/TRACEABILITY.md` | `REQ-V2-*` ↔ 代码文件/类 ↔ L1/实机测试 矩阵 | Lead |
| `docs/v2/CHANGELOG.md` | v2.0 → v2.1 及后续变更（日期/原因/影响） | Lead |
| `docs/VERIFICATION.md` | v2 实机证据（按轮次/截图/日志） | Lead |
| 本 §19 | 需求的唯一来源；其他文档只引用，不复制 | Lead |

规则：

- 每份文档头部写：`状态（draft/final）`、`日期`、`适用版本`、`变更摘要`。
- 文档之间用相对链接互引；同一事实只写一次，避免过期副本。
- 每个 v2 需求至少有一条测试映射；没有测试映射的需求不得标“已实现”。
- 文档使用 `【新增】/【修改】/【作废】/【待确认】` 标记变更，读者能一眼看出 v2 与 v1 的差异。

**B. 代码标记与注释**

- 每个新文件头部固定模板：

```csharp
// ============================================================================
// HDBF v2 | Layer: Core/Indoor | Owner: <name>
// Purpose: <一句话说明这个文件负责什么、不负责什么>
// Requirements: REQ-V2-CORE-01..05, REQ-V2-SAFE-01
// ============================================================================
```

- 关键行为处标 `// REQ-V2-...`，例如：
  - `// REQ-V2-CORE-03: never spawn world crops/fields`；
  - `// REQ-V2-WATER-02: tank deduction only in the daily tick`。
- **公开类型/方法必须有 XML 文档注释**（`/// <summary>`）；私有复杂逻辑注释解释“为什么”，不重复代码表面。
- 命名：意图清晰、避免自造缩写；统一术语（slot / tank / coverage / crop policy / roof stacking），与 §19.1 术语表一致。
- 魔法数字集中到 `IndoorConstants` / `TierCatalog` / 配置；禁止散落在逻辑里。
- `TODO`/`FIXME` 必须带 `REQ-V2-*` 或问题 ID；发布版不得有未登记 TODO；不得保留调试快捷键/开发者面板入口。
- 日志键固定并在 `docs/v2/ARCHITECTURE.md` 附录登记：`indoor.*`、`water.*`、`save.*`、`ui.*`、`compat.*`；同一 key 30 秒节流；日志带 entityId/槽位号等可定位信息，不带完整堆栈刷屏。

**C. UI 可读性**

- 面板显示单位/百分比/含义（例如“水罐 2.4/3.6 单位（约 2.0 天）”），不只显示裸数字。
- 失败原因必须具体：缺料（列出材料与数量）、缺水（水罐/水源/管道）、无工人、入口堵、输出库存满、槽位满。
- 空数据用“—”而不是 0；颜色不能是唯一信息载体（同时用图标/文字）。
- 中/繁/英三语键齐全；tooltip 与面板术语一致；不使用 v1 的“托管格/工作范围/开垦”等旧词。

**D. 可读性需求**

* `REQ-V2-READ-01`：上述文档集在阶段 1 结束时必须有骨架，阶段 4 前必须无占位符、无未登记 TODO。
* `REQ-V2-READ-02`：所有新增公开 API 有 XML 注释；所有需求在代码中有可检索的 `REQ-V2-*` 标记或测试映射。
* `REQ-V2-READ-03`：日志键/术语/单位统一且有登记；同一错误不重复刷屏。
* `REQ-V2-READ-04`：UI 失败原因与 tooltip 完整；三语本地化无缺键。
* `REQ-V2-READ-05`：变更文档（CHANGELOG/ADR）与行为同步；发布说明引用 REQ ID。

#### 19.18.2 可维护性与可扩展性（模组化 + 简单结构）

**A. 模块地图（保持 5 个程序集，不新增除非有充分理由）**

| 程序集 | v2 目录 | 职责 | 允许引用 |
|---|---|---|---|
| `HDBF.Core` | `Indoor/` | 槽位状态机、生长/水/疲劳/维护/动力公式、作物目录接口、存档记录模型、纯函数 | 仅 BCL；**禁止** UnityEngine / Timberborn |
| `HDBF.Persistence` | `Indoor/` | schema v2 编解码、v1→v2 迁移、字段校验/修复 | Core、游戏持久化接口 |
| `HDBF.Gameplay` | `Indoor/` | `IndoorFarmController`、日 tick 编排、水/库存/工人桥接、存档脏标记 | Core、Persistence、游戏程序集 |
| `HDBF.UI` | `Indoor/` | 面板快照/呈现、按钮命令、tooltip | Core、UI 框架程序集 |
| `HDBF.Integration` | `Indoor/` | 管道/动力/物流适配器（沿用 `ICompatAdapter`） | Core、反射访问外部模组 |

依赖方向：`Core ← Persistence ← Gameplay`；`Integration/UI → Core`；禁止反向引用与循环。Core 的“无 UnityEngine/游戏引用”由架构测试强制。

**B. 小接口（每个接口 ≤5 个方法、一屏可读完）**

| 接口 | 职责 | 备注 |
|---|---|---|
| `ICropCatalog` | 按阵营列作物、查 `GrowthTimeInDays`/产量/物品 ID | Core 定义；Gameplay 用游戏 spec 实现；缺 spec 有回退 |
| `IIndoorFarmState` | 只读槽位/水罐/维护/模式快照 | UI 与测试使用 |
| `IWaterSource` | `TryDraw(amount, out actual)` | 管道/人工/未来第三来源 |
| `IInventorySink` | `TryAdd(goodId, amount)` | 原版库存/传送带 |
| `IWorkScheduler` | 取下一个动作（播种/收获/补水） | 可单测的纯调度器 |
| `IIndoorPanelSnapshot` | 面板 DTO | UI 不直接读游戏对象 |
| `ISaveMigrator` | `TryMigrate(raw) → record` | v1→v2→v3 链 |

**C. 简单结构（优先“笨但清楚”的实现）**

- 组合优先，继承最多 1 层；不搞通用框架/事件总线/反射注入。
- 一个日 tick 编排器按固定顺序执行：水耗 → 生长 → 收获/播种 → 疲劳 → 维护/动力 → 存档脏标记；顺序固定且可测。
- 单文件 ≤300 行（软门槛）；超标必须按职责拆 partial 文件或独立类；禁止“上帝控制器”。
- 控制器只做编排，公式/状态迁移放在 Core 纯函数；Gameplay 只负责游戏对象/服务边界。
- 无静态可变状态；无每帧分配；无递归/死循环；缓存可显式清理。
- 不新增全局服务定位器；依赖通过构造注入；卸载/删除幂等。

**D. 扩展点（新增内容不改核心）**

- 档位/作物/水耗/维护/模式：来自 `TierCatalog` + `data/HDBF_Config.json` + 游戏 spec；新增档位或作物只加数据 + 测试，不改核心逻辑。
- 水源：新增 `IWaterSource` 实现即可（管道、人工、未来的水车/水箱）。
- 产物出口：新增 `IInventorySink` 实现即可（原版库存、传送带、未来仓库）。
- 存档：版本化 + 迁移链 + 未知字段忽略/保留；新字段必须有默认值，旧版可读。
- UI：通过 `IIndoorPanelSnapshot` 增加区块；不把游戏对象塞进 UI。
- 配置：新增配置键有 schema/范围/默认值；未知键忽略并记日志；错误配置回退默认。

**E. 可维护性/扩展性需求**

* `REQ-V2-MAINT-01`：Core 不得引用 UnityEngine/Timberborn；架构测试覆盖依赖方向与无环。
* `REQ-V2-MAINT-02`：单个实现文件 >300 行必须拆分或给出书面理由；控制器不得包含公式细节。
* `REQ-V2-MAINT-03`：一个日 tick 顺序固定；所有公式/状态迁移在 Core 纯函数中，可单测。
* `REQ-V2-MAINT-04`：无静态可变状态；无未受控的全局缓存；卸载/删除/重复初始化幂等。
* `REQ-V2-MAINT-05`：代码注释/文档/日志/命名遵循 §19.18.1；发布前清理调试代码与未登记 TODO。
* `REQ-V2-EXT-01`：新增档位/作物只能通过数据 + 测试完成，不得改核心公式代码。
* `REQ-V2-EXT-02`：水源/产物出口/适配器均通过接口扩展；新增实现不改现有调用方。
* `REQ-V2-EXT-03`：存档 schema 迁移链可追加；新字段有默认值；未知字段不导致失败。
* `REQ-V2-EXT-04`：配置键有 schema/范围/默认值；错误配置安全回退。

#### 19.18.3 安全性（防破坏存档 + 防崩溃）

**A. 防破坏存档（Save integrity）**

1. **版本化与迁移**：schema v2；迁移链幂等；未知字段忽略/保留；新字段有默认值；迁移前后都可读。
2. **写前校验（必须）**：数组长度 = Capacity；枚举白名单；浮点有限（非 NaN/Inf）；范围 clamp（`tank ≥ 0`、`fatigue 0..1`、`growth 0..GrowthTime`、`cyclesMissed 0..N`）；作物 ID 必须属于该阵营且存在，或为空；字符串长度上限；槽位索引不越界/不重复。
3. **失败安全**：字段缺失/类型错误/数组长度不符 → 安全默认值 + 节流警告 + 继续加载；单栋失败不影响其他建筑；v1 迁移失败 → **不覆盖旧记录**、建筑进入安全停用状态、允许拆除/重建；不得让存档无法加载。
4. **不删除玩家数据**：v2 不修改地形/地块/原版作物；v1 迁移释放的旧田块/作物保留为普通原版农田；拆除只销毁本建筑自己的记录。
5. **写入原子性**：只通过游戏持久化 API 写完整记录；序列化/校验失败时保留上一份良好快照（内存）与 dirty 标记，**绝不写半条记录**、绝不把异常抛进存档回调；下次保存重试并记日志。
6. **恢复路径**：迁移前只读校验；失败时 UI 显示“安全模式（空槽/默认维护）”；日志给出建筑坐标/ID/原因；依赖游戏自动存档做最终兜底。
7. **测试**：往返；截断数组；NaN/Inf；错误类型；非法枚举；长度 0/超长；重复/越界槽位；200 轮确定性损坏扫描；100×600 存档大小/耗时。

* `REQ-V2-SAVE-04`：写入前必须完成 §19.18.3-A2 的全部校验；任一失败不得写入该建筑记录，保留旧值并记 `save.validation-failed`。
* `REQ-V2-SAVE-05`：v1→v2 迁移失败必须保持旧记录可读、建筑安全停用、不删除玩家数据；不得抛异常。
* `REQ-V2-SAVE-06`：读档不得因缺失/损坏 HDBF 字段而失败；单栋隔离修复；修复摘要写入日志。
* `REQ-V2-SAVE-07`：损坏注入 / 迁移 / 往返 / 100×600 预算测试必须全绿，且纳入发布门禁。

**B. 防崩溃（Crash resistance）**

1. **边界 try/catch**：日 tick、save/load、activate/deactivate/delete、UI 刷新、命令、适配器调用全部捕获；异常不外抛；节流日志；不得静默吞掉（至少 `HDBF/Warn` 一次）。
2. **隔离**：每槽位、每建筑、每适配器、每 UI 区块独立 try/catch；单点失败不拖垮其他；连续 3 次失败禁用该子系统并显示警告，游戏继续。
3. **资源/性能**：日 tick 纯数组遍历、无每帧分配/字符串拼接；有界循环；无递归/死循环；缓存可清理；卸载/删除幂等；无静态可变状态。
4. **空值/生命周期**：服务、实体、组件、蓝图 spec、适配器结果都可能缺失；全部 null 检查；实体销毁后安全 no-op；重复加载/卸载/拆建幂等。
5. **补丁与外部**：v2 目标 **0 Harmony**；适配器只反射、失败降级；Core 不引用外部模组；缺失模组不影响运行。
6. **配置安全**：非法/缺失配置回退默认 + 警告；不因配置导致崩溃/坏档。
7. **UI 安全**：数据未就绪显示“—”；UI 异常不影响模拟；UI 不做重活/不抛异常。
8. **测试**：fault injection（空服务、缺 spec、损坏存档、适配器抛异常、库存满、实体销毁、重复加载/卸载、无工人、无水源）；实机矩阵零未捕获异常。

* `REQ-V2-SAFE-01`：所有游戏边界必须有 try/catch 与节流日志；禁止未捕获异常进入 Tick/存档/加载/UI。
* `REQ-V2-SAFE-02`：单槽位/单建筑/单适配器失败必须隔离；连续 3 次失败只禁用该子系统并显示警告，不得崩溃或坏档。
* `REQ-V2-SAFE-03`：日 tick 无每帧分配；循环有界；无递归/死循环；卸载/删除幂等。
* `REQ-V2-SAFE-04`：所有跨游戏对象访问有 null 检查；实体销毁后安全 no-op。
* `REQ-V2-SAFE-05`：v2 不新增 Harmony 补丁；适配器反射失败必须降级，Core 不引用外部类型。
* `REQ-V2-SAFE-06`：配置文件非法/缺失时回退默认并记日志；不得崩溃。
* `REQ-V2-SAFE-07`：UI 异常/数据缺失不得影响模拟；面板失败时显示安全占位。
* `REQ-V2-SAFE-08`：fault injection 套件必须全绿，并作为发布门禁。
