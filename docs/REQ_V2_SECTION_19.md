
## 19. v2 修订（2026-10-25 初版 / v2.1 2026-10-26）：3×3×1 室内高密度农场

> **状态**：v2.1-draft（设计评审中，尚未实现）。本章是 v1 的正式修订；**本章与 §1–§18 冲突时以本章为准**，本章未改写的条款继续有效。
>
> **v2.1 变更（2026-10-26，用户反馈）**：建造工时由 **6/10/16/28 工日缩短为 2/3/5/8 工日**；新增 **§19.18 非功能需求**（可读性 / 可维护性 / 可扩展性 / 安全性）；其余设计不变。
>
> **依据（用户 2026-10-25 决定）**：
> 1. 采用 **D 方案**：作物与农田不再位于建筑外面；四档的 60/150/300/600 个种植位改为**建筑内部的抽象高位槽位**，农民在建筑**室内**种植与采集。
> 2. 屋顶**平的、无作物、无凸起**，顶面可通行并可**叠放建筑**。
> 3. 四档占地统一改为 **3×3×1**（原 3×2×1 作废）。
>
> **范围**：建筑规格、室内作物模拟、水/劳动力/平衡、存档、UI、美术与测试。**不改**原版作物、物品、资源与全局数值。

### 19.1 设计摘要

* 建筑是一个 3×3×1 的“盒子农场”。内部有按档位配置的 **60 / 150 / 300 / 600 个室内槽位**（抽象的高密度货架/培育位，不逐个占用世界格）。建筑**不再**有工作范围、托管格、地块注册、可达性扫描、地块高亮、田块翻耕或世界作物实体。
* 农民是建筑的工作位工人；农事（播种/收获）在建筑内部完成。没有“入口到地块”的外部寻路与通勤。
* 作物生长由模组在建筑内部模拟：每个槽位记录作物、生长进度、疲劳与上一茬作物；读取原版作物的 `GrowthTimeInDays`、产量与产物定义，保证与原版作物经济一致。
* 收获产物进入建筑的 `SimpleOutputInventory`，再由原版搬运/物流适配器送出；模组不直接改全局资源计数。
* 水、维护、动力、疲劳、轮作、模式与停摆沿用 v1 的数值与惩罚框架，但**灌溉**改为内部水罐 + 管道/人工补水，不再读取外部土壤水分。
* 屋顶是一个干净的平平台：顶面可通行、可作为上方建筑的支撑面；屋顶上**不允许**出现作物、设备或高于 1.0 格的装饰。

> ⚠️ **设计偏离声明**：v1 的“不凭空产作物、只收真实世界作物、农民必须走到地块”三条底线在本方案中被有意替换为“室内真实生长模拟 + 农民在建筑内作业”。这不是遗漏，而是用户明确选择的 D 方案。v2 的防作弊底线改为：无工人不作业、无水不生长、无维护会减产/停摆、无动力顶级减产、产物只能来自成熟槽位的模拟收获。

### 19.4 室内槽位模型（替代托管格）

* **槽位**是纯逻辑单位：`SlotIndex`（0..Capacity-1）、`CropTemplateId`、`GrowthProgressDays`、`Stage`（Empty/Growing/Mature）、`Fatigue`、`LastCropTemplateId`、`ReservedByWorker`。
* 槽位**不映射世界格**；没有 `PlotId`、没有坐标、没有注册表、没有扫描。
* 有效槽位：`P_eff = min(Capacity, ActiveWorkers × 38)`；只有前 `P_eff` 个槽位参与农事调度，其余槽位是“容量储备”，面板显示“已配置/上限”。
* 槽位顺序稳定：0..Capacity-1 固定，不因读档/重排改变；新播种优先使用编号最小的空槽。
* **不建地块、不生成原版作物实体、不设置 `ITerrainService.SetField`**。

`REQ-V2-CORE-01`：槽位数量等于档位 Capacity，四档 60/150/300/600；`P_eff` 必须随在岗农民数实时变化，且产出只统计前 `P_eff` 个槽位。

`REQ-V2-CORE-02`：读档后槽位数组长度必须等于 Capacity；缺字段按“空槽 + 疲劳 0”补齐；数组长度不一致时截断/补齐并记录警告，不得抛异常。

### 19.5 作物与室内生长模拟

**作物数据来源**

* 运行时读取当前阵营 `FarmHouse` 可种作物集合（原版 `PlantableSpec.ResourceGroup = Farmhouse`），以及每个作物的 `GrowableSpec.GrowthTimeInDays`、`CuttableSpec.Yielder.Yield`（物品 ID 与数量）。
* 允许的作物：
  * Folktails：Carrot、Potato、Wheat、Sunflower（以实际 spec 为准）；
  * IronTeeth：Canola、Cassava、Corn、Eggplant、Kohlrabi、Soybean（以实际 spec 为准）。
* 找不到 spec 时使用内置回退表（生长天数/产量与 v1 目标一致），并记一次 `HDBF/Warn`；不得崩溃。

**生长公式（v2）**

```text
G_growth = G_irr × G_maint × G_power            // 生长速度乘数
progressDays += ΔgameDays × G_growth            // 只在有作物且未成熟时推进
G_fat    = 1 − 0.60 × F
yield    = BaseYield × G_fat × G_mode            // 收获时结算
G_mode   = 1.00（常规/休耕） / 1.35（密植）
```

* `G_irr` 由内部水罐覆盖率按 §19.7 的公式计算；`G_maint` 1.0/0.5/0；`G_power` 1.0/0.6。
* `G_growth = 0` 时生长停止（不推进），但作物不消失；恢复后继续。
* 成熟：`progressDays ≥ GrowthTimeInDays` → `Stage=Mature`；等待农民收获。
* 收获：占用一次农事动作；产物进入建筑输出库存；若库存满则**不收获**，槽位保持成熟，面板显示积压。
* 轮作：收获后记录 `LastCropTemplateId`；若作物策略为轮作，下一个空槽/下一茬选择与上一茬不同的作物；疲劳增量 ×0.4 并在收获后 `F −= 0.05`（沿用 v1 数值）。
* 疲劳：同一槽位连续种同一作物 `F += 0.08 × 档位疲劳系数`（封顶 1.0）；`F` 只影响产量，不影响生长速度（v2 明确）。
* 模式：密植 `yield ×1.35`，但水耗 ×1.5、疲劳积累 ×1.5、每动作工时 ×1.2；休耕不播种/不收获，`F` 每日 −0.03，水耗 30%。

`REQ-V2-CORE-03`：禁止调用 `NaturalResourceFactory.PlantNew`、原版种植/收获任务、`PlantingService.SetPlantingCoordinates`、`ITerrainService.SetField` 或任何世界田块 API；v2 的作物只存在于槽位数据中。

`REQ-V2-CORE-04`：生长/收获/疲劳/轮作必须是**纯逻辑**（放在 `HDBF.Core`，不引用 UnityEngine/游戏对象），可用 L1 测试在任意帧率下得到确定结果。

`REQ-V2-CORE-05`：任何槽位的异常（作物 spec 缺失、数值非法、数组越界）不得中断其他槽位或抛进游戏主循环；单槽隔离 + 节流警告。

### 19.6 水罐、补水与灌溉覆盖率

* v2 **没有自然灌溉/土壤水分**；水完全由内部水罐提供。
* 水罐容量（单位）与满负荷天数沿用 §19.3 表。
* 每日水耗：`demandDay = 活跃槽位数 × WaterPerSlotPerDay × modeWaterFactor`（密植 ×1.5，休耕 ×0.3）。
* 覆盖率：`C = clamp(tank / demandDay, 0, 1)`；当日结算时若 `tank ≥ demandDay` 则扣 `demandDay`、`C=1`，否则 `C=tank/demandDay`、`tank=0`。
* 灌溉乘数沿用 v1：`G_irr = clamp((C − 0.25×C_min) / (0.75×C_min), 0, 1)`；`C < 0.25×C_min` 时 `G_irr=0`。
* **补水路径**：
  1. **管道补水（Timber Pipes 适配器）**：连接时按当日需求自动补水（上限为当日需求，不囤积超过水罐容量）；无水源/断开时降级并警告。
  2. **人工补水**：无管道时，玩家可点“补水”；工人每趟从 12 格内的可用水源（水体/水泵/水罐）取水，增加 `TankCapacity / 3` 单位（≈1 个满负荷日），消耗 2 个农事动作 + 外部往返；水源被污染或不存在时按钮禁用并给出原因。
* **不得无源补水**；管道与人工补水都必须有真实水源。
* 干旱只影响外部水源/管道供水，不直接“晒死”室内槽位；水罐是缓冲。
* `REQ-V2-WATER-01`：覆盖率必须由纯函数计算；`tank=0` 时 `C=0`、`G_irr=0`，不得除零/负值。
* `REQ-V2-WATER-02`：水罐只能通过管道或人工补水增加；每日扣水一次，禁止逐帧扣水。
* `REQ-V2-WATER-03`：面板必须显示水罐单位、可支撑天数、`C`、`C_min`、补水来源与缺水警告；`C < C_min` 时显示减产比例。
* `REQ-V2-WATER-04`：补水动作可以被工人执行，但不得让工人“瞬移”到水源；往返时间计入动作预算，路径不可达时补水失败并提示。

### 19.7 劳动力与室内作业

* 工人上限 2/4/8/16；`P_eff = min(Capacity, ActiveWorkers × 38)`。
* 每日动作预算：`actionsDay = ActiveWorkers × 13`；每次播种或收获计 1 个动作。
* 单动作工时：`workCost = 0.08 × modeWorkFactor`（常规/休耕 1.0，密植 1.2）；**无路径项**。
* 优先级：成熟待收 > 空槽待播 > 补水；同级按槽位编号稳定排序，保证确定性。
* 无工人/全部离岗：不得播种、不得收获、不得产出；已有作物仍可按 §19.5 生长（无维护停摆只停农事，不停止生长，沿用 v1）。
* 工人必须在建筑工作位在岗（原版 workplace 门禁）；工人不足时面板显示积压动作数。
* `REQ-V2-LABOR-01`：动作预算必须按在岗工人数×13/日，收获优先；不得跨日超发。
* `REQ-V2-LABOR-02`：`workCost` 不含路径项；v1 的 `REQ-BAL-04/06` 作废。
* `REQ-V2-LABOR-03`：工人的所有表现（是否在岗、是否有工作位）沿用原版 workplace 规则；模组不得让工人“凭空在建筑里工作”而不占工作位。

**算例**：顶级 16 人 × 38 = 608 → 600 槽；16×13=208 动作/日；600 槽若 6 天一轮、每槽 2 次动作 = 1200 动作/6 日 = 200/日，刚好饱和——与 v1 相同，保留“缺勤即积压”的敏感度。

### 19.8 维护、动力、模式与停摆（沿用 v1 数值）

### 19.9 农民与建筑内部表现

* 农民从建筑入口进出；建筑工作位在模型内部/门口，不需要走到世界地块。
* 不再有“入口到地块”的外部路径、寻路失败、可达性拒绝或地块高亮。
* 室内作物表现：
  * 模型可提供固定的货架/培育床**装饰**（不按槽位动态生成 600 个模型）；
  * 面板/世界不需要逐个槽位的视觉映射；
  * 室内作物是否可见由美术决定（见 §19.11 与待确认项 §19.15），不影响模拟。
* `REQ-V2-LABOR-04`：农民在建筑内工作期间必须保持原版工作动画/工作位占用；不得让农民在室外农田上执行 v2 农事。

### 19.10 存档（schema v2）

**`HDBF` 根节点**：

```json
{
  "schemaVersion": 2,
  "buildings": [
    {
      "entityId": "...",
      "tier": "Basic|Intermediate|Advanced|Top",
      "faction": "Folktails|IronTeeth",
      "mode": "Normal|Dense|Fallow",
      "cropPolicy": "Rotation|Fixed",
      "fixedCrop": "Carrot|...|",
      "tank": 3.6,
      "maintenance": { "dueDay": 12.0, "cyclesMissed": 0 },
      "power": { "connected": false, "mode": "Grid|OffGrid" },
      "ports": { "pipe": false, "logistics": false, "power": false },
      "slots": [
        { "crop": "Carrot", "growth": 1.25, "fatigue": 0.16, "lastCrop": "Potato", "flags": 0 }
      ],
      "adapters": { "TimberPipes": "Degraded" }
    }
  ]
}
```

* `slots` 长度必须等于档位 Capacity（60/150/300/600）；空槽的 `crop` 为空串、`growth=0`、`fatigue` 保留。
* 不写 `plotIds`/坐标/世界格；v2 存档不包含任何地块引用。
* 存档大小：600 槽 × 单槽约 20–24 bytes（作物 ID 内联 + 3 个数值 + 标志）≈ 12–15 KB/栋；100 栋 ≈ 1.2–1.5 MB，落在 v1 第 12.7 节的 1.0–1.4 MB 目标带内（略微上浮需在实现时按实际序列化测量，若超限则对作物 ID 做字典内联/压缩）。
* `REQ-V2-SAVE-01`：schema v2 必须可读、可写、可往返；字段缺失/类型错误/数组长度不符必须做安全修复并记 `HDBF/Warn`，不得坏档。
* `REQ-V2-SAVE-02`：v1 → v2 迁移（尽力而为）：
  * v1 的 `plots.ids/crops/fatigue` 按顺序映射到 v2 槽位（数量取 `min(v1 plot 数, Capacity)`），`tank`、维护、模式、端口、适配器保留；
  * v1 曾由 HDBF 注册的外部地块**不再归 HDBF 管理**；HDBF 不删除地块上的原版作物/田块（留给玩家作为普通农田），只清掉 HDBF 注册表；
  * 迁移失败时该建筑以“空槽 + 满水罐 + 默认维护”安全状态载入，并记一次 `HDBF/Warn`，不得导致存档无法加载。
  * 若用户确认“v1 存档不兼容”，可改为拒绝加载 v1 HDBF 实体并记录；默认采用尽力迁移。
* `REQ-V2-SAVE-03`：读档后槽位、水罐、疲劳、维护、模式、端口必须与存档数值一致（浮点按存档精度）；日 tick 结果与 30/144 fps 无关。

### 19.11 UI 与本地化

**建筑面板字段**：

| 区块 | 内容 |
|---|---|
| 头部 | 档位、阵营、工人 `W/W_max`、模式（常规/密植/休耕） |
| 槽位 | 上限、已配置、有效槽位 `P_eff`、空槽、生长中、可收获、积压 |
| 正在生长 | 每个当前占用的作物一行：作物名、生长中槽数、待收槽数、平均生长进度条；第一格种下即出现 |
| 水 | 水罐单位、可支撑天数、覆盖率 `C`、`C_min`、补水来源（管道/人工/无）、缺水警告 |
| 维护 | 到期日、逾期周期、缺料；按钮“执行维护” |
| 动力 | 已接电/离网/断电；顶级 |
| 作物策略 | 轮作（默认）/固定作物下拉；当前轮作序列 |
| 输出 | 输出库存占用、端口状态 |
| 操作 | 补水、维护、模式切换；不提供“重扫地块/显示托管格/框选” |

* **删除** v1 §14.4/§14.5 的地块高亮、框选、世界地块图标与“已注册/可开垦/已排除”数值。
* 世界空间 P0/P1 图标仅保留：缺水、维护逾期、动力不足/断电、入口堵塞；不再有“托管格不足”。
* 面板数据由 `HDBF.Core` 的快照提供；UI 层不直接读游戏对象；`REQ-V2-UI-01`：面板刷新 ≤4 Hz、脏标记、无分配抖动。
* `REQ-V2-UI-02`：作物策略/补水/维护按钮必须给出明确失败原因（缺水、缺料、无源、无工人、入口堵）。
* `REQ-V2-UI-03`：新增本地化键：内部槽位、水罐、补水、作物策略、轮作、固定作物、覆盖率等；中/繁/英三语必须齐全。
* `REQ-V2-UI-04`：面板与提示不得再出现“工作范围/托管格/开垦/地块高亮”等 v1 术语（本地化与 tooltip 一并清理）。
* `REQ-V2-UI-05`：面板必须有「正在生长」卡片，**从第一格种下起**按作物逐行显示当前实际生长状态
  （作物名、生长中/待收槽数、平均生长进度 `0..100%`），并随面板 4 Hz 刷新更新，不得等种植槽种满才显示；
  无作物时显示明确的空状态行。数据只来自快照（`IndoorFarmSnapshot.Crops`），UI 不读槽位数组；
  作物 spec 缺失时该作物仍列出、进度按 0 计算，单项异常不得影响其他作物行或抛出到面板（REQ-V2-SAFE-01）。

### 19.12 美术与模型

* 3×3×1 外包络；正面入口；四个侧立面与屋顶；8 个成品模型（4 档 × 2 阵营）+ 8 个施工阶段模型。
* **屋顶**：平的，顶面为最高面（建议 y=1.00），可通行/可叠建筑；无作物、无通风塔、无设备、无高过 1.0 的装饰；边缘收边 ≤0.04 且不得阻断上方放置。
* **室内表现**：模型正面/侧面可开窗或开放式展示室内货架/培育床；作物是**装饰**，不按 600 槽动态生成；具体“可见/半可见/封闭”见 §19.15 待确认项。若做开放展示，必须保证不把装饰当作可收获物或可点击实体。
* 四档材质/构型区分（木架/温室玻璃/金属/工业），50% 镜头可辨；LOD0 为主，LOD1/2 由游戏自动优化或后续补；材质仍用原版 `MaterialCollection` 名称（不需 Unity/AssetBundle），自订 PBR 材质仍延后。
* 端口：水/灌溉（全档）、物流输出（中级起）、动力（顶级）；空节点 `#Port#Power/#Port#Pipe/#Port#Logistics` 保留；与 v1 端口坐标契约保持可对照，但需按 3×3 新模型重定坐标。
* `REQ-V2-ART-01`：模型外包络不超过 3×3×1；屋顶顶面 30cm 内不得有几何（可叠放 A/B 必须通过）。
* `REQ-V2-ART-02`：16 个 `.timbermesh` 导出可加载；无 crop-slot 节点；蓝图路径/图标/验证器同步。
* `REQ-V2-ART-03`：施工阶段必须有灰盒；完工替换不得抛 slot/端口异常。
* `REQ-V2-ART-04`：四档 50% 镜头可辨（轮廓/材质/开窗/端口），并出预览渲染图供用户确认后再实机。

### 19.13 兼容与性能

**兼容**

* 五个适配器保留：Timber Pipes（水罐补水，**变为关键路径**）、Power Lines（顶级动力）、Conveyor Belts V2（输出物流）、More Mines（资源 ID 校验）、Hooman Stairs（入口/屋顶叠放的通行探测）。
* 不再有外部灌溉采样、外部地块、作物实体或可达性扫描；v1 的对应降级逻辑删除。
* 适配器缺失时必须降级为：管道=人工补水；动力=离网 0.6；物流=原版库存；不得阻断建筑运行。
* `REQ-V2-COMPAT-01`：适配器探测/初始化/失败隔离/报告字段沿用 v1 §11.7 的 `ICompatAdapter` 契约；核心程序集不得引用外部模组类型。
* `REQ-V2-COMPAT-02`：管道/动力/物流端口无对应模组时隐藏或置灰，不显示“缺少模组”错误（沿用 v1）。
* `REQ-V2-COMPAT-03`：屋顶叠放与 Hooman Stairs 的交互必须在实机矩阵中验证；上层建筑被拆/堵时，下层盒子农场不得崩溃。

**性能**

| 项 | 预算 |
|---|---|
| 100 栋 × 600 槽日 tick | ≤0.5 ms/建筑/日（纯数组遍历；摊销到每日） |
| 覆盖率重算 | 2 Hz/建筑，O(activeSlots)；≤0.05 ms/建筑 |
| UI 刷新 | ≤4 Hz，脏标记；≤0.10 ms/建筑 |
| 无逐帧全图扫描 | v2 不扫描世界 |
| 存档 | 100 栋 ≤1.5 MB；序列化 ≤50 ms（沿用 v1 预算） |
| 叠放 nav mesh | 上层建筑放下后一次重建；不得每帧重建 |

`REQ-V2-PERF-01`：100 栋顶级建筑 + 100 个上层建筑的场景必须稳定 60 fps 目标（低端机可按 v1 降频策略），并在实机 Profiler 测量；`REQ-V2-PERF-02`：日 tick 只遍历 `Capacity` 数组，不得创建临时列表/字符串拼接；`REQ-V2-PERF-03`：叠放不得导致寻路/网格重建抖动。

### 19.15 实施阶段与风险

**阶段**

1. **v2 Core 纯逻辑**：槽位/生长/水/劳动力/维护/动力/存档编解码 + L1 测试；不碰游戏。
2. **数据与美术**：8 蓝图改 3×3×1 + 可叠顶面；16 个 `.timbermesh`；图标；验证器；预览给用户确认。
3. **Gameplay/UI/存档**：室内农事控制器；删除扫描/地块/作物可见性/原版种植派发；水罐/补水；面板；v1→v2 迁移。
4. **实机**：TC-V2-01..10；性能；兼容矩阵；部署。

**主要风险**

| 风险 | 缓解 |
|---|---|
| 屋顶叠放在 Timberborn 1.1.2.8 不允许“工作建筑上再放建筑” | 先用原版最小建筑 A/B；失败则报告用户，选择“加薄平台（2 高）”或降低要求（§19.3 已登记） |
| D 方案被指“隐藏产出/作弊” | 保留工人/水/维护/动力四道门禁；产物只来自成熟槽位；面板显示积压与惩罚；文档记录偏离 |
| v1→v2 存档迁移造成旧农场异常 | 尽力迁移 + 失败安全默认 + 不删除玩家原版作物/田块 + 备份 |
| 600 槽 ×100 栋性能/存档膨胀 | 纯数组日 tick、作物 ID 内联、实测预算；超限则压缩/共享 |
| 3×3 模型在 1 格高内表达“室内高密度”不足 | 用开窗/货架剪影/材质分层；50% A/B 验收；必要时做内部装饰层 |
| 水罐/补水让水利玩法变弱或变重 | 管道=自动化、人工=有成本；水罐 3–4 天缓冲；干旱仍影响水源 |

**B. 代码标记与注释**

- 每个新文件头部固定模板：

```csharp
// ============================================================================
// HDBF v2 | Layer: Core/Indoor | Owner: <name>
// Purpose: <一句话说明这个文件负责什么、不负责什么>
// Requirements: REQ-V2-CORE-01..05, REQ-V2-SAFE-01
```

  - `// REQ-V2-CORE-03: never spawn world crops/fields`；

- **公开类型/方法必须有 XML 文档注释**（`/// <summary>`）；私有复杂逻辑注释解释“为什么”，不重复代码表面。
- 命名：意图清晰、避免自造缩写；统一术语（slot / tank / coverage / crop policy / roof stacking），与 §19.1 术语表一致。
- 魔法数字集中到 `IndoorConstants` / `TierCatalog` / 配置；禁止散落在逻辑里。
- `TODO`/`FIXME` 必须带 `REQ-V2-*` 或问题 ID；发布版不得有未登记 TODO；不得保留调试快捷键/开发者面板入口。

**C. UI 可读性**

- 面板显示单位/百分比/含义（例如“水罐 2.4/3.6 单位（约 2.0 天）”），不只显示裸数字。
- 失败原因必须具体：缺料（列出材料与数量）、缺水（水罐/水源/管道）、无工人、入口堵、输出库存满、槽位满。
- 空数据用“—”而不是 0；颜色不能是唯一信息载体（同时用图标/文字）。
- 中/繁/英三语键齐全；tooltip 与面板术语一致；不使用 v1 的“托管格/工作范围/开垦”等旧词。

**D. 可读性需求**

* `REQ-V2-READ-01`：上述文档集在阶段 1 结束时必须有骨架，阶段 4 前必须无占位符、无未登记 TODO。

#### 19.18.2 可维护性与可扩展性（模组化 + 简单结构）

**A. 模块地图（保持 5 个程序集，不新增除非有充分理由）**

| 程序集 | v2 目录 | 职责 | 允许引用 |
|---|---|---|---|
| `HDBF.Core` | `Indoor/` | 槽位状态机、生长/水/疲劳/维护/动力公式、作物目录接口、存档记录模型、纯函数 | 仅 BCL；**禁止** UnityEngine / Timberborn |
| `HDBF.Persistence` | `Indoor/` | schema v2 编解码、v1→v2 迁移、字段校验/修复 | Core、游戏持久化接口 |
| `HDBF.Gameplay` | `Indoor/` | `IndoorFarmController`、日 tick 编排、水/库存/工人桥接、存档脏标记 | Core、Persistence、游戏程序集 |
| `HDBF.UI` | `Indoor/` | 面板快照/呈现、按钮命令、tooltip | Core、UI 框架程序集 |
| `HDBF.Integration` | `Indoor/` | 管道/动力/物流适配器（沿用 `ICompatAdapter`） | Core、反射访问外部模组 |

依赖方向：`Core ← Persistence ← Gameplay`；`Integration/UI → Core`；禁止反向引用与循环。Core 的“无 UnityEngine/游戏引用”由架构测试强制。

**B. 小接口（每个接口 ≤5 个方法、一屏可读完）**

| 接口 | 职责 | 备注 |
|---|---|---|
| `ICropCatalog` | 按阵营列作物、查 `GrowthTimeInDays`/产量/物品 ID | Core 定义；Gameplay 用游戏 spec 实现；缺 spec 有回退 |
| `IIndoorFarmState` | 只读槽位/水罐/维护/模式快照 | UI 与测试使用 |
| `IWaterSource` | `TryDraw(amount, out actual)` | 管道/人工/未来第三来源 |
| `IInventorySink` | `TryAdd(goodId, amount)` | 原版库存/传送带 |
| `IWorkScheduler` | 取下一个动作（播种/收获/补水） | 可单测的纯调度器 |
| `IIndoorPanelSnapshot` | 面板 DTO | UI 不直接读游戏对象 |
| `ISaveMigrator` | `TryMigrate(raw) → record` | v1→v2→v3 链 |

**C. 简单结构（优先“笨但清楚”的实现）**

- 组合优先，继承最多 1 层；不搞通用框架/事件总线/反射注入。
- 一个日 tick 编排器按固定顺序执行：水耗 → 生长 → 收获/播种 → 疲劳 → 维护/动力 → 存档脏标记；顺序固定且可测。
- 单文件 ≤300 行（软门槛）；超标必须按职责拆 partial 文件或独立类；禁止“上帝控制器”。
- 控制器只做编排，公式/状态迁移放在 Core 纯函数；Gameplay 只负责游戏对象/服务边界。
- 无静态可变状态；无每帧分配；无递归/死循环；缓存可显式清理。
- 不新增全局服务定位器；依赖通过构造注入；卸载/删除幂等。

**D. 扩展点（新增内容不改核心）**

- 档位/作物/水耗/维护/模式：来自 `TierCatalog` + `data/HDBF_Config.json` + 游戏 spec；新增档位或作物只加数据 + 测试，不改核心逻辑。
- 水源：新增 `IWaterSource` 实现即可（管道、人工、未来的水车/水箱）。
- 产物出口：新增 `IInventorySink` 实现即可（原版库存、传送带、未来仓库）。
- 存档：版本化 + 迁移链 + 未知字段忽略/保留；新字段必须有默认值，旧版可读。
- UI：通过 `IIndoorPanelSnapshot` 增加区块；不把游戏对象塞进 UI。
- 配置：新增配置键有 schema/范围/默认值；未知键忽略并记日志；错误配置回退默认。

**E. 可维护性/扩展性需求**

* `REQ-V2-MAINT-01`：Core 不得引用 UnityEngine/Timberborn；架构测试覆盖依赖方向与无环。
* `REQ-V2-MAINT-02`：单个实现文件 >300 行必须拆分或给出书面理由；控制器不得包含公式细节。
* `REQ-V2-MAINT-03`：一个日 tick 顺序固定；所有公式/状态迁移在 Core 纯函数中，可单测。
* `REQ-V2-MAINT-04`：无静态可变状态；无未受控的全局缓存；卸载/删除/重复初始化幂等。
* `REQ-V2-MAINT-05`：代码注释/文档/日志/命名遵循 §19.18.1；发布前清理调试代码与未登记 TODO。
* `REQ-V2-EXT-01`：新增档位/作物只能通过数据 + 测试完成，不得改核心公式代码。
* `REQ-V2-EXT-02`：水源/产物出口/适配器均通过接口扩展；新增实现不改现有调用方。
* `REQ-V2-EXT-03`：存档 schema 迁移链可追加；新字段有默认值；未知字段不导致失败。
* `REQ-V2-EXT-04`：配置键有 schema/范围/默认值；错误配置安全回退。

#### 19.18.3 安全性（防破坏存档 + 防崩溃）

**A. 防破坏存档（Save integrity）**

1. **版本化与迁移**：schema v2；迁移链幂等；未知字段忽略/保留；新字段有默认值；迁移前后都可读。
2. **写前校验（必须）**：数组长度 = Capacity；枚举白名单；浮点有限（非 NaN/Inf）；范围 clamp（`tank ≥ 0`、`fatigue 0..1`、`growth 0..GrowthTime`、`cyclesMissed 0..N`）；作物 ID 必须属于该阵营且存在，或为空；字符串长度上限；槽位索引不越界/不重复。
3. **失败安全**：字段缺失/类型错误/数组长度不符 → 安全默认值 + 节流警告 + 继续加载；单栋失败不影响其他建筑；v1 迁移失败 → **不覆盖旧记录**、建筑进入安全停用状态、允许拆除/重建；不得让存档无法加载。
4. **不删除玩家数据**：v2 不修改地形/地块/原版作物；v1 迁移释放的旧田块/作物保留为普通原版农田；拆除只销毁本建筑自己的记录。
5. **写入原子性**：只通过游戏持久化 API 写完整记录；序列化/校验失败时保留上一份良好快照（内存）与 dirty 标记，**绝不写半条记录**、绝不把异常抛进存档回调；下次保存重试并记日志。
6. **恢复路径**：迁移前只读校验；失败时 UI 显示“安全模式（空槽/默认维护）”；日志给出建筑坐标/ID/原因；依赖游戏自动存档做最终兜底。
7. **测试**：往返；截断数组；NaN/Inf；错误类型；非法枚举；长度 0/超长；重复/越界槽位；200 轮确定性损坏扫描；100×600 存档大小/耗时。

* `REQ-V2-SAVE-04`：写入前必须完成 §19.18.3-A2 的全部校验；任一失败不得写入该建筑记录，保留旧值并记 `save.validation-failed`。
* `REQ-V2-SAVE-05`：v1→v2 迁移失败必须保持旧记录可读、建筑安全停用、不删除玩家数据；不得抛异常。
* `REQ-V2-SAVE-06`：读档不得因缺失/损坏 HDBF 字段而失败；单栋隔离修复；修复摘要写入日志。
* `REQ-V2-SAVE-07`：损坏注入 / 迁移 / 往返 / 100×600 预算测试必须全绿，且纳入发布门禁。

**B. 防崩溃（Crash resistance）**

1. **边界 try/catch**：日 tick、save/load、activate/deactivate/delete、UI 刷新、命令、适配器调用全部捕获；异常不外抛；节流日志；不得静默吞掉（至少 `HDBF/Warn` 一次）。
2. **隔离**：每槽位、每建筑、每适配器、每 UI 区块独立 try/catch；单点失败不拖垮其他；连续 3 次失败禁用该子系统并显示警告，游戏继续。
3. **资源/性能**：日 tick 纯数组遍历、无每帧分配/字符串拼接；有界循环；无递归/死循环；缓存可清理；卸载/删除幂等；无静态可变状态。
4. **空值/生命周期**：服务、实体、组件、蓝图 spec、适配器结果都可能缺失；全部 null 检查；实体销毁后安全 no-op；重复加载/卸载/拆建幂等。
5. **补丁与外部**：v2 目标 **0 Harmony**；适配器只反射、失败降级；Core 不引用外部模组；缺失模组不影响运行。
6. **配置安全**：非法/缺失配置回退默认 + 警告；不因配置导致崩溃/坏档。
7. **UI 安全**：数据未就绪显示“—”；UI 异常不影响模拟；UI 不做重活/不抛异常。
8. **测试**：fault injection（空服务、缺 spec、损坏存档、适配器抛异常、库存满、实体销毁、重复加载/卸载、无工人、无水源）；实机矩阵零未捕获异常。

* `REQ-V2-SAFE-01`：所有游戏边界必须有 try/catch 与节流日志；禁止未捕获异常进入 Tick/存档/加载/UI。
* `REQ-V2-SAFE-02`：单槽位/单建筑/单适配器失败必须隔离；连续 3 次失败只禁用该子系统并显示警告，不得崩溃或坏档。
* `REQ-V2-SAFE-03`：日 tick 无每帧分配；循环有界；无递归/死循环；卸载/删除幂等。
* `REQ-V2-SAFE-04`：所有跨游戏对象访问有 null 检查；实体销毁后安全 no-op。
* `REQ-V2-SAFE-05`：v2 不新增 Harmony 补丁；适配器反射失败必须降级，Core 不引用外部类型。
* `REQ-V2-SAFE-06`：配置文件非法/缺失时回退默认并记日志；不得崩溃。
* `REQ-V2-SAFE-07`：UI 异常/数据缺失不得影响模拟；面板失败时显示安全占位。
* `REQ-V2-SAFE-08`：fault injection 套件必须全绿，并作为发布门禁。
